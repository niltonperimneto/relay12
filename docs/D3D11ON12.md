# D3D11On12 on D3DMetal

## Status

This document describes the design and implementation status of D3D11On12 in
`winecx-gptk`. The implementation is experimental and is not yet capable of
returning a functional D3D11On12 device.

The current code establishes a safe routing and versioning boundary. It must
continue returning `DXGI_ERROR_UNSUPPORTED` until it can return genuine D3D11
interfaces backed by the caller's D3D12 device and command queue.

## Objective

Support Windows applications that call `D3D11On12CreateDevice` while using
Apple D3DMetal as the D3D12 implementation:

```text
Windows application
    -> d3d11.dll router
    -> Wine D3D11 runtime/DDI host
    -> Microsoft D3D11On12 DDI
    -> Microsoft D3D12TranslationLayer
    -> caller's D3DMetal ID3D12Device and direct command queue
    -> D3DMetal
    -> Metal 4 when Whisky supplies D3DM_MTL4=1
```

The feature is D3D11-on-D3D12. It is not D3D12-on-D3D11.

## Non-negotiable invariants

- Use the exact `ID3D12Device` supplied by the application.
- Submit work through the supplied direct `ID3D12CommandQueue`.
- Do not create an independent WineD3D, DXVK, or D3D12 device as a fallback.
- Do not return success with incomplete or fabricated COM objects.
- Preserve COM identity and reference-counting rules.
- Initialize every requested output before returning failure.
- Propagate device removal and submission failures.
- Do not redistribute Apple D3DMetal or proprietary WDK headers.
- Preserve normal Apple D3D11 behavior outside `D3D11On12CreateDevice`.

## Verified behavior of the Apple payload

GPTK 4.0 beta 2 was imported and deployed to the Whisky canary runtime. Whisky
correctly configured the tested D3DMetal bottle with:

- `D3DM_MTL4=1`
- `D3DM_FORCE_D3D11=1`
- builtin overrides for `d3d11`, `d3d12`, and `dxgi`
- production validation layers disabled

Apple's PE `d3d11.dll` exports exactly:

| Ordinal | Export |
| ---: | --- |
| 1 | `D3D11CreateDevice` |
| 2 | `D3D11CreateDeviceAndSwapChain` |
| 3 | `D3D11On12CreateDevice` |

Static inspection shows that Apple's `D3D11On12CreateDevice` immediately
returns `0x887a0004`, `DXGI_ERROR_UNSUPPORTED`. It does not invoke
`libd3dshared.dylib`.

The conformance probe could not run in the coding sandbox because Wine failed
to register its wineserver Mach port. This is an execution-environment
restriction rather than a missing payload or incorrect Whisky configuration.

## Why Microsoft's source is not sufficient by itself

Microsoft D3D11On12 is a D3D11 user-mode DDI driver. Its primary entry point is
`OpenAdapter_D3D11On12`; it is not the public Windows `d3d11.dll` runtime.

On Windows, the proprietary D3D11 core runtime:

1. validates public D3D11 API calls;
2. creates runtime handles and callback tables;
3. loads the D3D11On12 driver;
4. translates public COM calls into D3D11 DDI calls;
5. manages public COM objects, identity, and lifetimes.

Wine does not currently provide this DDI-host architecture. Its public D3D11
implementation calls WineD3D directly. Therefore, using Microsoft's mapping
layer requires a new host backend beneath Wine's D3D11 frontend.

DXVK cannot serve as the D3DMetal host unchanged. Its D3D11On12 path requires
vkd3d-proton's private `ID3D12DXVKInteropDevice` to import Vulkan objects.
D3DMetal does not expose that interface.

## Implemented components

### Conformance probe

`tests/d3d11on12probe.c` exercises:

- D3D12 device and direct queue creation;
- `D3D11On12CreateDevice`;
- `ID3D11On12Device` discovery;
- wrapped BGRA render-target creation;
- acquire, clear, release, and flush;
- D3D12 fence completion.

CI cross-compiles and retains the probe as an artifact.

### D3D11 router

`gptk-d3d11/d3d11shim.cpp` is a low-level C++17 PE router. It:

- preserves Apple's export names and ordinals;
- forwards ordinary D3D11 creation to `d3d11mt.dll`;
- routes `D3D11On12CreateDevice` to `d3d11on12core.dll`;
- uses a versioned C ABI;
- clears On12 outputs before failure;
- returns `DXGI_ERROR_UNSUPPORTED` when no compatible core exists;
- uses no exceptions or RTTI;
- is audited for accidental `libstdc++` and `libgcc_s` dependencies.

The original Apple forwarder must be renamed to `d3d11mt.dll` during
transactional deployment.

### Core boundary

`gptk-d3d11/d3d11on12core.cpp` exports:

- `WineD3D11On12GetABIVersion`
- `WineD3D11On12CreateDeviceV1`
- `WineD3D11On12GetInterface`, which publishes the size/versioned
  `WineD3D11On12Interface` function table

The current core validates:

- output initialization;
- non-null D3D12 device and queue inputs;
- exactly one queue for the initial supported configuration;
- `ID3D12Device` and `ID3D12CommandQueue` interfaces;
- direct command-queue type;
- queue/device COM identity;
- single-bit node masks;
- feature-level array consistency and D3D12 support.

Interface queries are propagated rather than flattened: a device object that is
not an `ID3D12Device`, or a queue object that is not an `ID3D12CommandQueue`,
yields that `QueryInterface` result instead of a generic `E_INVALIDARG`. A
success code returned with no interface breaks the COM contract, but this
boundary faces a proprietary payload, so it is treated as `E_NOINTERFACE`
instead of being dereferenced.

After validation, it intentionally returns `DXGI_ERROR_UNSUPPORTED`. The
success path must not be enabled until the DDI host produces genuine objects.

### Diagnostics

Neither module is a Wine builtin, so Wine's `ERR` and `TRACE` macros are not
available to them. Both report through `OutputDebugStringA`, which reaches the
same debug output and adds no import beyond `kernel32`. The reported
conditions are the ones that would otherwise fail silently:

- `d3d11mt.dll` missing, or missing an expected creation export, which means
  Apple's forwarder was not renamed correctly at deployment;
- `d3d11on12core.dll` present but publishing an incompatible interface table,
  which means a mismatched deployment;
- inputs accepted but no DDI host implemented, so the milestone's
  `DXGI_ERROR_UNSUPPORTED` is not mistaken for a driver or application bug.

### Core validation tests

`tests/d3d11on12coretest.c` links the core directly and drives it with mock
`ID3D12Device`, `ID3D12CommandQueue`, and plain `IUnknown` objects, so every
validation and fail-closed rule is exercised without a GPU, a D3D12 runtime, or
the Apple payload. The mock vtables are designated initializers with unused
slots left null, so a call the core is not expected to make faults instead of
passing unnoticed.

It covers the ABI version, interface-table negotiation, argument validation,
non-D3D12 inputs, non-direct and foreign-device queues, node masks,
feature-level forwarding and failure propagation, output initialization on
every failure path, optional outputs, and reference-count balance across
repeated calls. CI links it with the C driver, which also proves the core
needs no C++ runtime, and runs it under Wine.

### Clean-room DDI layout harness

`gptk-d3d11/ddi/wine_d3d11ddi.h` holds the clean-room rules and the
`WINE_DDI_ASSERT_*` size, alignment, and field-offset macros that every future
DDI declaration group must use. No group is declared yet.

`tests/d3d11ddilayout.c` is the harness's own test: it compiles as both C and
C++ and checks at run time that the macros' compile-time answers match the
layout a real object has, so a broken macro cannot make future offset
assertions vacuous. CI additionally refuses any declaration group that lacks a
`Specification` and `Retrieved` provenance block.

## Language and ABI policy

- Use low-level C++17 for the router and implementation.
- Export only `extern "C"` entry points.
- Do not allow C++ exceptions, C++ types, or allocator ownership across DLL
  boundaries.
- Compile the router with exceptions and RTTI disabled.
- Avoid static objects with nontrivial constructors and destructors.
- Use MinGW-w64 GCC for PE binaries; do not switch the Wine PE build to
  LLVM-MinGW.
- Prefer fixed-size, versioned ABI structures before the ABI becomes stable.

C++26 is not the production baseline. Its MinGW/GCC support is less stable and
it provides no necessary feature that C++17 lacks for this component.

## Remaining implementation

### 1. Strengthen the core ABI

Done. `WineD3D11On12GetInterface` negotiates a structure carrying its own
size, the ABI version, capability flags, function pointers, and reserved
zero-initialized fields; the router rejects unexpected sizes, unknown
versions, and missing required entry points, and a rejected table publishes no
entry points.

The remaining rule is procedural: bump `WINE_D3D11ON12_ABI_VERSION` whenever
the table's layout or the meaning of a field changes, and keep the header's
offset assertions in step with it.

### 2. Clean-room DDI declarations

The harness and provenance gate exist; no declaration group does. Implement
only the selected D3D11 DDI version and required declarations:

- adapter, device, context, and resource handles;
- runtime callback tables;
- adapter and device function tables;
- resource, view, shader, state, query, and command structures;
- version negotiation constants;
- DXGI DDI interoperability structures.

Every declaration group must cite its public specification in the provenance
block CI enforces, and assert its size, alignment, and every field offset with
the `WINE_DDI_ASSERT_*` macros. An unasserted field is not acceptable: a wrong
offset in a DDI structure is silent memory corruption, not a compile error. A
private authorized WDK job may compare generated metadata, but it must never
upload WDK content.

### 3. Port D3D12TranslationLayer

- replace ATL and `CComPtr` dependencies;
- remove ETW and telemetry integration from this build;
- replace unsupported MSVC extensions and helper APIs;
- port DXBC parsing dependencies;
- eliminate MSVC runtime imports;
- retain upstream MIT notices and a reviewable patch series;
- build reproducibly with MinGW-w64 GCC C++17.

### 4. Port Microsoft D3D11On12

- compile against the clean-room DDI declarations;
- replace `_com_error` and other MSVC-only behavior;
- convert exceptions to `HRESULT` at the exported boundary;
- select and freeze one DDI interface version;
- disable unsupported display-kernel paths;
- retain the supplied device, queue, and node information.

### 5. Implement the Wine D3D11 DDI host

Refactor Wine's D3D11 frontend behind an internal backend operations table.
Keep WineD3D behavior unchanged and add a D3D11On12 backend that:

- calls `OpenAdapter_D3D11On12`;
- provides runtime adapter and device callbacks;
- allocates DDI private storage;
- translates public D3D11 calls into DDI calls;
- constructs `ID3D11Device` and `ID3D11DeviceContext`;
- exposes `IDXGIDevice` and `ID3D11On12Device` with correct COM identity;
- initially supports one node, one direct queue, and the immediate context.

Deferred contexts must return a truthful unsupported result until their full
recording and replay semantics are implemented.

### 6. Wrapped resources

Each wrapped resource must retain:

- the original `ID3D12Resource`;
- its owning D3D12 and D3D11On12 devices;
- requested D3D11 interface and flag overrides;
- input and output D3D12 resource states;
- acquired or released ownership state;
- subresource state and in-flight lifetime data.

The ownership sequence is:

```text
D3D12-owned
    -> AcquireWrappedResources
    -> transition from declared input state
    -> D3D11-owned
    -> D3D11 commands
    -> ReleaseWrappedResources
    -> transition to declared output state
    -> flush/submit on the caller's queue
    -> D3D12-owned
```

Reject cross-device resources, double acquisition, unmatched release,
unsupported interfaces, and incompatible flags.

### 7. Queue synchronization

- serialize On12 submissions with use of the supplied queue;
- batch command lists and resource barriers;
- allocate monotonic fence values;
- recycle allocators only after fence completion;
- retain referenced resources until GPU completion;
- propagate device removal;
- wait during teardown when required;
- avoid CPU waits on ordinary submission paths.

### 8. Whisky deployment and capability gating

Deployment must be transactional:

1. validate the D3DMetal payload and runtime compatibility;
2. rename Apple's `d3d11.dll` to `d3d11mt.dll`;
3. install the router and compatible core;
4. verify hashes, ordinals, and Wine builtin markers;
5. run the end-to-end capability probe;
6. record `supportsD3D11On12` only after the probe passes;
7. restore the original payload atomically on any failure.

Initially require an explicit experimental setting. The implementation must
not infer support merely because `D3D11On12CreateDevice` is exported.

`D3DM_MTL4=1` remains controlled by Whisky. The core must not set or override
it. When enabled, On12-generated D3D12 work reaches Metal 4 because it uses the
caller's existing D3DMetal device.

## Testing strategy

### Static and build gates

- exact submodule revisions and license files;
- prohibited WDK-file detection;
- provenance blocks on every DDI declaration group;
- MinGW warnings as errors;
- the core validation tests and the DDI layout harness, built and run under
  Wine on every pull request;
- exact PE export names and ordinals;
- imported-DLL allowlists;
- no unintended C++ runtime dependency;
- Wine builtin marker validation;
- deterministic source and binary inputs.

### Core tests

Implemented in `tests/d3d11on12coretest.c`, which covers:

- null and inconsistent arguments;
- unsupported ABI version and size;
- non-D3D12 devices and queues;
- non-direct queues;
- queue from another device;
- invalid node masks;
- unsupported feature levels;
- output initialization on every failure;
- omitted optional outputs;
- objects that violate the COM contract by reporting success with no
  interface;
- feature-level array forwarding and propagated query failures;
- COM identity and reference-count stress.

The mock COM objects need no GPU, no D3D12 runtime, and no Apple payload, so
the suite runs on any pull request. It is not a substitute for the graphics
conformance work below: it can only prove the boundary rejects what it must
and never returns success.

### Graphics conformance

- wrap buffers and textures;
- render-target clear and pixel readback;
- input/output state restoration;
- multiple subresources;
- D3D12 work before and after D3D11 work;
- fence completion on the original queue;
- repeated creation and destruction;
- concurrent submission;
- forced device removal;
- Direct2D and DirectWrite over a wrapped swap-chain buffer.

Successful API calls alone are insufficient. Tests must verify rendered data,
queue identity, resource states, and fence completion.

### Application validation

- Microsoft's D3D1211On12 sample;
- Chromium/CEF surfaces;
- Unity and Unreal initialization;
- video and UI middleware;
- representative D3D12 games;
- D3DMetal with Metal 4 both enabled and disabled.

## Rollout stages

1. **Development:** core disabled; mock and compile-time tests only.
2. **Experimental:** explicit opt-in after the conformance probe passes.
3. **Canary:** enable for pinned GPTK/runtime combinations with diagnostics and
   atomic rollback.
4. **Stable:** enable only after middleware, game, device-loss, and long-running
   regression tests pass.

## Security and Hardening Audit

Given the integration of D3D11On12 over **D3DMetal (GPTK4)** on **ARM macOS** (handling Windows `x86_64` code executed via Rosetta 2 or potential future native ARM64), the following architectural elements have been audited. They must be hardened prior to pushing the Canary stage to Production:

### 1. D3DMetal COM Abstraction Tolerances
**Audit Finding:** Apple's proprietary D3DMetal payload is known to occasionally return `S_OK` during `QueryInterface` on D3D12 devices while providing a `NULL` pointer.
**Status:** **Mitigated.** The core boundary (`d3d11on12core.cpp`) currently verifies both the `HRESULT` and the pointer explicitly (`if (FAILED(hr) || !device12.get())`). This perfectly handles D3DMetal's edge-case COM violations defensively.

### 2. DXGI HRESULT Error Mapping for API Fallbacks
**Audit Finding:** `d3d11shim.cpp` handles missing underlying `d3d11mt.dll` exports by returning `HRESULT_FROM_WIN32(ERROR_PROC_NOT_FOUND)`.
**Hardening Action:** D3DMetal-aware game engines rely heavily on strict DXGI error codes to orchestrate graceful API downgrades. When executed under Rosetta 2, unexpected file error codes may cause engines to fatally abort before initiating a fallback loop. Map these shim initialization failures directly to `DXGI_ERROR_UNSUPPORTED` (`0x887A0004`).

### 3. Telemetry Evasion via `OutputDebugStringA`
**Audit Finding:** The implementation utilizes `OutputDebugStringA` because the PE DLLs act as standalone Windows wrappers rather than Wine-builtin modules.
**Hardening Action:** Many games intercept `OutputDebugStringA` on their own hook, which risks burying deployment errors. For robust GPTK4 telemetry via Wine on Rosetta 2, dynamically resolve `__wine_dbg_output` from `ntdll.dll` inside the shim logic. This guarantees that D3D11On12 initialization errors are reliably routed to Wine's native `WINEDEBUG` trace streams for end-user diagnostics.

### 4. DDI Alignments on ARM Boundaries
**Audit Finding:** The clean-room headers (`wine_d3d11ddi.h`) use standard C-struct packing assumptions which are correctly checked during `x86_64-w64-mingw32` compilation.
**Hardening Action:** As GPTK and Whisky progressively transition toward native ARM APIs and memory management requirements (e.g. potential Windows ARM64 deployment), explicitly wrap all WDK DDI declarations in `#pragma pack(push, {expected})` and `#pragma pack(pop)`. This guarantees that `gcc` will perfectly mirror the Windows MSVC tight-packing rules, eliminating the risk of mismatched alignment failures on AArch64 hardware.
